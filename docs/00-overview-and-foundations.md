# Overview and foundations

[Documentation index](README.md)

HelloFHE starts with one synchronous encrypted computation: admit `x` in `0..100`, encrypt it, evaluate `x * x + x`, decrypt and compare the result. Clef functions coordinate the experiment. Packed execution, cache-aware SIMD and an actor service extend that first working boundary. The cryptographic implementation is first-party Clef in Fidelity.Cryptography. HelloFHE is also a proving workload for Tier 1-4 instrumentation in the PSG and SMT lowering through MLIR. The source is a draft. These documents specify its contracts and implementation sequence; execution evidence is pending.

The CPU and GPU documents date their original publication to September 2025 and record subsequent implementation reviews. They describe the integration points and target requirements. Execution evidence for the full cache policy and heterogeneous actor path is still required. Proposed attributes such as `CacheLineAligned` and `L1Resident` are not new source requirements for HelloFHE.

Range and depth constrain the cryptographic representation. Representation determines coefficient storage and evaluation-key traffic. Storage and liveness constrain tiling and concurrency, which guide actor placement. Track those dependencies together.

## Existing cryptography foundation

[Fidelity.Cryptography](../../Fidelity.Cryptography/README.md) is present as a first-party peer of Fidelity.Platform. Its current work includes scalar SHA-256, candidate-provider selection, a HACL hash binding pilot, operation contracts, custody/entropy design and MBS sealing design. Its README reports a native hash smoke with open range findings and no accepted cryptographic provider. HelloFHE still requires its own acceptance evidence.

The inspected portfolio and operation contracts cover hashes, authenticated encryption, KEMs, signatures, derivation and randomness. The executable [candidate contracts](../../Fidelity.Cryptography/src/Core/Contracts.clef) currently select AEAD suites; they do not declare FHE contexts, evaluation keys or homomorphic operations. Fidelity.Cryptography needs an FHE operation contract and Clef implementation covering the selected scheme, encoding, parameters, key purposes, evaluation operations and verification requirements. Use its custody, entropy, buffer-completion and provider-substitution contracts. A software FHE key is usable only under a policy that permits its representation and operations; a generic protected-key handle does not establish FHE support.

Platform supplies target and environment premises. The selected [Linux x86_64 profile, lines 1-21](https://forge.spkez.dev/FidelityFramework/Fidelity.Platform/src/commit/8452124a5af4fb0d5d289d6f16ab47d23a07ed10/Profiles/Linux_x86_64_Default/Fidelity.Platform.fidproj#L1-L21) selects the libc environment, description and bindings; it does not select a cryptographic suite or an FHE provider. The present HelloFHE manifest therefore remains a clear-reference project. Add a Cryptography dependency when its required FHE contract/provider exports exist and are selected. The current scaffold package does not implement FHE encryption.

MBS sealing uses Cryptography's [existing sealing contract](../../Fidelity.Cryptography/docs/mbs-sealing.md). An outer authenticated storage envelope and the inner FHE ciphertext serve different purposes. An authorized storage reader can open that envelope and still hold only FHE ciphertext; it does not acquire the client's FHE decryption key. Keep the key purposes, context identity and recovery policies separate.
